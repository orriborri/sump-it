Problem: The interface between frontend and backend exists only as URL strings and any, so every Rust change can silently break the UI.

Solution: Pick one way to generate the TypeScript side of the seam from the Rust types, and delete the tRPC/tarpc leftovers that aren't used.

  • Leverage: one contract, every call site typed
  • Locality: breaking changes fail at compile time
  • Delete 3 unused dependencies
Decision needed: tRPC needs a TypeScript server, so it can't run directly on a Rust backend. The options are a tRPC-style Rust library (rspc), generated types plus typed fetch (BeanIt already used ts-rs + OpenAPI), or a thin TypeScript tRPC layer in front of Rust.

Problem: The recipe rules are spread across four modules. They're also wrong for half the brewing methods: a 15–17 ratio and a 150 g water minimum make Espresso (about 1:2), Moka and ColdBrew impossible to log.

Solution: Put all recipe rules, keyed by brewing method, behind one module. The database checks only the invariants that can never vary.

  • Locality: rule changes happen once
  • Tests hit one interface
  • Fixes the Espresso/ColdBrew bug

Problem: Bean inventory is enforced twice with opposite behaviour. The in-memory check rejects a short bag, while the SQL clamps to 0. Nothing ties the insert and the decrement into one transaction.

Solution: One module owns logging a brew, including the stock check and the decrement, and does both in one transaction.

  • Locality: inventory bugs live in one place
  • Two adapters: Postgres and a test DB
  • Session duplication reuses it for free

Problem: Prisma, inline DDL and the structs each define the tables differently. For example, the Rust enums serialise as burrConical while Postgres stores BurrConical, and the DB adds a roast_date <= purchase_date rule that the models don't know about.

Top recommendation

A. Give the frontend ↔ backend seam a real contract

The type-safe seam between TypeScript and Rust was the main reason for the consolidation, and right now it doesn't exist. How it's generated decides where the Brew recipe (B) and Brew log (C) types live, so settle it first. D is a cheap deletion that can happen alongside it.
